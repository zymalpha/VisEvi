# MedVisEvi 方法框架

> 版本：v1.2（2026-11-02）
> 工作目录：`/ssd/visual_reasoning/zym/MedVisEvi`
> 本文只介绍项目的方法框架和信息流，不替代工具矩阵、功能规格或独立评估协议。

## 1. 要解决的问题

胸片上的一个业务问题通常不能由单个模型直接可靠地回答。以心胸比为例，系统至少需要知道投照类型、图像质量、心影边界和胸廓内缘；以病灶侧别为例，需要把病灶候选与左右肺放到同一个坐标系中；以随访变化为例，还需要确认两张片属于同一患者、时间顺序正确、投照可比、图像已经配准并且两次观察指向同一个病灶。

因此，项目不把模型输出直接当作最终答案，而是把回答拆成三个问题：

1. 图像中有哪些可追溯的局部观察？
2. 哪些确定性规则可以从这些观察推导出测量或空间关系？
3. 在适用条件、冲突和证据缺失的情况下，系统是否应该回答、限定回答或拒答？

MedVisEvi 的目标是把这三个问题写成可执行、可复算、可审计的证据程序。最终结果应能回溯到输入图像、工具版本、模型身份、参数、坐标、单位、运行记录和拒答原因。

选择分为三个层次：五个独立类别 Gate 判断是否启用 Q/P/T/S/G，各类别内再选择闭集业务功能，最后由版本化 `FunctionSpec` 和依赖图展开 A 工具。类别 Gate 的网络与可选桥接已实现，编码器、训练与校准暂缓；默认 VQA 仍采用规则路由。模型不能绕过功能协议直接生成视觉事实或跳过检查条件。

## 2. 总体方法

系统采用“工具层—功能协议层—证据图层—消费层”的分层结构：

```text
胸片与任务请求
        │
        ▼
需求路由：五类 Gate 选类别 → 类内规则选功能编号
（网络可选接入；默认规则基线；未训练 Gate 拒绝执行）
        │
        ▼
FunctionSpec：声明输入、工具依赖、输出、适用条件和拒答规则
        │
        ▼
A 工具层：生成 mask、点、框、属性、几何量和质量量
        │
        ▼
证据标准化：原图坐标、单位、状态、来源和图像绑定
        │
        ▼
确定性关系程序：距离、比例、重叠、分布或时间差
        │
        ▼
EvidenceGraph：Observation → Relation → Claim
        │
        ▼
EvidenceCard：按功能协议渲染可核验的证据卷宗
        │
        ▼
消费模型：接收问题、原图和证据卷宗，结合判断并引用证据
        │
        ▼
核验器：检查引用、数值、单位、方向和拒答条件
```

`EvidenceSession` 是一次执行的中心对象。它保存任务需求、证据图、工具调用轨迹、程序轨迹和最终判定；模型后端不能绕过会话对象单独写入无法追踪的结论。

上图中的 EvidenceCard、消费模型和核验器是下游方法层。VQA API 已把 26 项功能接入统一的 EvidenceCard、consumer 和 verifier；Q4 使用 `q4-response-2`，其他功能使用 `function-response-1`，核验完整结构化输出与 Claim 绑定。该核验不独立验证图像语义、A 工具或医学准确性，也没有自动冲突仲裁。当前自然语言槽位抽取、多功能联合回答和真实模型评估仍未完成。相关证据子图选择、输入模式与实验设计详见[VQA 图像、问题与证据联合输入方案](VQA图像问题与证据联合输入方案.md)。

### 2.1 一次功能执行的步骤

一次执行可以按下面的顺序理解。前一步的结果是后一步的前提；无法满足必需前提时，流程应停止并记录拒答。

| 步骤 | 输入 | 系统动作 | 形成的结果 |
|---|---|---|---|
| 1. 明确请求 | 图像、功能编号或查询、功能参数 | `RuleRouter` 在已登记的 26 项目录中解析功能；多义或未知请求不会猜测 | 明确的功能 ID，或 `ambiguous` / `unknown` |
| 2. 检查功能协议 | `FunctionSpec`、运行时 A 工具注册表 | 检查规格、工具是否存在、参数是否符合 schema、步骤 DAG 是否有效 | 可执行的工具步骤及 required closure |
| 3. 绑定输入 | 图像文件、finding、方向/配对等可信元数据 | 计算图像内容哈希；检查已有会话是否仍绑定同一图像；成对功能分别创建 prior/current 会话 | 图像与会话角色明确的执行上下文 |
| 4. 收集观察 | 规格中的 A 工具步骤 | 按稳定拓扑顺序调用工具；必要时只复用仍与注册表、图像、参数、mask 和产物绑定的成功调用 | Observation、运行时 mask/landmark、调用轨迹 |
| 5. 计算功能关系 | 已收集的 Observation 和功能程序 | 检查实际使用的观察、坐标、单位、边界和数值；按确定性规则计算比例、距离、空间或时间关系 | 带 `rule_id` 和上游节点引用的 Relation |
| 6. 给出有限声明 | Relation、规格 guards 和 validity conditions | 检查声明范围没有超过输入证据；通过图校验后才创建 Claim | 支持当前功能命题的结构化 Claim，或拒答 |
| 7. 保存可审计结果 | 节点、边、工具轨迹、程序轨迹、verdict | 保存 `session.json` 与 `episode.json`；成对试点也保存 prior 会话 | 可检查的执行记录和拒答原因 |

这里的“成功”指执行器得到结构完整、内部一致的证据程序结果。它不代表模型观察一定符合真实解剖，也不代表 Claim 已通过临床准确性验证。

### 2.2 当前功能选择与工具选择的边界

功能路由和 A 工具规划不是同一件事：

- **选功能**：调用方显式传入 `P9` 是最可复现的方式；也可按规格关键词查询。当前 `RuleRouter` 只做闭集规则匹配，不使用生成式模型来猜功能。
- **选类别**：可注入五个独立类别 Gate；每个 Gate 只输出对应类别的启用分数，允许多选或全不选。当前 `CategoryFunctionGate` 在单个所选类别内调用规则路由，多类别结果明确拒绝进入单功能 VQA，不增加现有 runner 的功能允许范围。
- **选工具**：功能已经确定后，工具步骤来自对应 JSON `FunctionSpec`。例如 P9 的程序明确规定 A24、A25、A2 和 A12；执行器不会因语言模型临时建议而偷偷增加另一个工具。
- **选工具参数**：固定参数写入规格，例如 P6 的 A6 finding 固定为 `pneumothorax`；由调用者提供的变量则通过 `$input.xxx` 解析，并在运行前对照 A 工具 schema 校验。
- **决定可否继续**：required 步骤缺失或拒答会阻断该功能；optional 步骤失败只记录缺失项，不能伪造 Observation。

这让一项功能可以被重复执行和审查：输入和工具链固定后，结果变化应能追踪到图像、模型/权重、参数或程序版本，而不是隐含的临场规划。

## 3. A 工具层：产生局部证据元件

A1–A26 是基础工具，不是最终业务答案。它们可以来自模型，也可以是确定性图像/几何计算。输出形式可能是：

- 空间 mask，例如肺野、心影或候选区域；
- 点或关键点，例如隆突、导管尖端和解剖标志；
- 框，例如病灶候选框；
- 属性或类别，例如 PA/AP、原始质量量和设备类别；
- 数值，例如宽度、距离、纹理或灰度统计；
- 与结果绑定的元数据，例如原图坐标系、单位、视野截断、阈值、模型版本和缓存身份。

每个 A 工具必须在接口层明确以下内容：

1. 输入图像类型和预处理方式；
2. 输出字段、坐标约定、单位和数值含义；
3. 原始分数是否校准；
4. mask、点或框是否绑定到当前图像和当前工具调用；
5. 哪些输入缺失、越界、截断、无法解析或来源不一致时必须拒答。

模型输出是预测证据，不能因为字段名叫 probability 就自动当作校准概率。确定性工具也不能因为公式正确，就被解释为医学结论；其准确性取决于输入的 mask、点或框是否可靠。

可以把 A 工具理解为“类型明确的测量仪器”，而不是一条诊断结论。例如 A6 输出的是 CheXOne 对某个 finding 的候选框和解析状态，框并集 mask 只是候选框栅格化结果；A9 能准确计算这个 mask 的宽度，但 A9 无法把候选框变成真实结节边界。于是 A6 的检测性能、A9 的几何实现、以及两者组成的功能表现必须分别验证。

不同 A 工具的结果要组合，至少要满足三个绑定条件：

1. **对象绑定**：工具结果指向正确的 anatomy/finding；例如候选 mask 必须绑定产生它的 A6 Observation。
2. **图像绑定**：mask、点、框属于当前图像或明确标注的 prior/current 图像，不能只因大小相同就混用。
3. **表示绑定**：坐标系、边界约定和单位一致；像素距离与毫米距离不可混写，框并集与真实轮廓不可互换。

像素口径、侧别约定、模型视野等具体实现约定参见[项目介绍](项目介绍.md)和[A 工具详细说明与评估矩阵](A工具详细说明与评估矩阵.md)。

## 4. FunctionSpec：把业务功能写成协议

每个 Q/P/T/S/G 功能由一份版本化 `FunctionSpec` 描述，文件位于 `src/visevi/functions/specs/`。规格至少包含：

| 部分 | 含义 |
|---|---|
| 功能身份 | 编号、类别、命题和版本 |
| 输入类型 | 单图、成对图或时间序列 |
| 工具步骤 | 必需/可选工具、参数和上游依赖 |
| 输出 | 结构化字段、单位和状态 |
| 槽位 | finding、region、measurement、device、condition、comparison 等 |
| guards | 运行前必须满足的适用条件 |
| refusal_rules | 证据不足、冲突或不适用时的拒答行为 |
| evaluation_protocol | 参照、指标、数据划分、统计和冻结状态 |
| blockers | 当前不能宣称完成的原因 |

规格存在不等于执行器存在，执行器存在也不等于医学准确性已经通过。当前统一入口已注册全部 26 项；T4 是显式 caller-reference adapter，缺少 reference 时拒答，尚无自动胸腔引流管模型。已接入程序通过合成契约测试；Q/P 另有开发集流程触发，这只验证软件接线、证据契约和拒答，不代表医学准确性。

### 4.1 如何把一个业务问题写成功能规格

建立功能规格时，先把自然语言问题缩成可测量的目标，再依次确定：

1. **目标范围**：它要判断类别、给出位置、测量数值，还是比较时间变化？输出是单个候选、区域并集还是病例级状态？
2. **最小输入**：单张片还是成对图像？是否必须有 finding、可信方向、study 时间、配准或其他元数据？
3. **证据依赖**：哪些 A 工具产生所需观察？哪些计算需要上游 mask/点？required 与 optional 的划分依据是什么？
4. **计算口径**：公式、坐标、单位、缺失值、边界条件和冲突状态如何定义？如果口径尚未确定，先输出原始量或拒答，不发明阈值。
5. **允许声明**：最终 Claim 到什么层次为止？例如“测得 CTR=…”不自动升级为“心脏扩大”。
6. **评估参照**：哪类独立人工标注可以判断这个输出？连续测量用什么误差指标？分类用什么标签？哪些图像不适用？

规格中的 `evaluation_protocol` 目前仍为草案，并不自动配置数据或触发医学评估。冻结参照、患者级划分、指标和统计口径，必须发生在使用锁定测试集之前。

### 4.2 功能不是工具清单

多个工具只有在它们共同回答一个明确问题时才组成一项功能。功能程序需要说明各观察之间的关系，而不仅仅是“先调用 A1、再调用 A6”。例如：

- A1 生成左右肺 mask；
- A6 生成异常候选框及框并集 mask；
- A21 分别计算候选与两侧肺 mask 的重叠；
- G1 根据这两个关系输出图像侧，并在输入方向得到独立核实时才映射到患者侧。

这个例子的关键方法是“互补观察 + 明确关系 + 输出边界”：A1 提供解剖参照，A6 提供候选区域，A21 提供可计算空间关系，G1 将关系限定为侧别证据。每个环节的缺失和失败都有独立处理方式。文末的功能示例将逐步展开更多实例。

## 5. 依赖图与规则路由

### 5.1 依赖图

`DependencyGraph` 在任何工具运行前检查步骤 ID、依赖是否存在、依赖闭包和环。它输出稳定的拓扑顺序。同一个工具可以在不同步骤出现，因为不同步骤可能使用不同参数、输入角色或上游证据。

必需步骤会带上所有上游依赖。必需工具拒答时，当前功能停止并返回结构化 `ToolRefusal`；可选工具失败时只进入缺失清单，不得伪造一个成功观察替代它。

### 5.2 规则路由

`RuleRouter` 是闭集路由器：

- 显式功能编号是最可复现的入口；
- 自然语言请求只按规格中登记的关键词匹配；
- 多个功能同时匹配时返回 `ambiguous`，不会猜测；
- 未知功能编号返回 `unknown`，不会静默回退到相近功能。

VQA 层已有 `RuleFunctionGate`，在目录关键词之外提供 Q4/P9 别名、显式编号优先和候选冲突拒绝。它仍是默认入口。

可选的类别前置模块已经实现：`FiveCategoryGates` 接收共享问题向量，Q/P/T/S/G 各使用参数独立的线性层或二层 MLP，分别产生一个 logit；独立 Sigmoid 和可配置阈值形成类别集合。部署接口记录 logits、分数、阈值、类别和版本；没有已训练权重时返回 `untrained`。分数没有校准，不作为医学证据可信度，也不用于加权工具 Claim。实现与接入方式见[五类 Gate 网络调研与实现](五类Gate网络调研与实现.md)。

标注路由监督或最终回答 loss 监督尚未选择；当前仅网络前向保留梯度，硬选择、外部工具和文本生成之间没有端到端可微训练链路。未来意图解析和槽位抽取也必须经过 schema 与闭集校验。

## 6. 三层证据图

### 6.1 Observation

Observation 是 A 工具或可信外部输入直接提供的事实，例如：

- 当前图像的 Right_Lung mask；
- A6 返回的 nodule 候选框；
- A24 解析出的 PA；
- A26 给出的 ETT 尖端点和隆突点；
- 调用方提供的已核实配准记录。

Observation 必须带有来源工具或来源记录、图像绑定、有效性条件和必要的 provenance。它可以引用缓存或 artifact，但外部引用必须使用明确的前缀，不能伪装成图内节点。

### 6.2 Relation

Relation 是由一个或多个已有 Observation 经过确定性规则得到的结果，例如：

- 心影宽度除以胸廓宽度得到 CTR；
- 候选框与左右肺的像素交集；
- ETT 尖端与隆突点之间的欧氏距离；
- prior/current 框宽高和灰度均值之差；
- A8 和 A6 的通道一致或冲突状态。

Relation 必须把输入节点写入 `provenance` 和 `input_ids`，并在图中建立带规则 ID 的边。任何缺失输入、坐标不一致、单位不明或结果与原始 mask 不一致，都应拒绝生成 Relation。

### 6.3 Claim

Claim 是面向功能命题的结构化声明，例如“本次图像具备带条件的 CTR 测量证据”或“该候选在图像左侧”。Claim 只能由 Relation 和/或 Observation 支持，必须保留支持、反对、适用条件和规则版本。

Claim 不等于临床诊断。Claim 及其来源是模型综合原图与工具证据时的可核验依据，不是取代原图的答案。当前 Q4 协议会保留模型答案和 Claim 一致性判定；后续应独立保存模型视觉观察和工具 Claim 的冲突状态。系统需保留 `not_assessed`、`limited`、原始分数和拒答状态，避免把测量结果、模型分数或几何关系扩展成未验证的临床解释。

## 7. 统一执行入口

`run_function_episode()` 负责一次功能 episode 的完整生命周期：

1. 解析功能编号或规则查询；
2. 加载并校验 FunctionSpec；
3. 创建或复用 `EvidenceSession`；
4. 计算图像哈希和工具调用缓存键；
5. 按依赖图顺序运行必需/可选步骤；
6. 原子提交 Observation、mask 和 landmark；
7. 对工具拒答、非法输出和图结构错误进行结构化处理；
8. 执行该功能的确定性关系程序；
9. 创建 Relation 和 Claim；
10. 保存 session、episode、调用轨迹和证据引用。

单图功能使用 `current` 会话。S1 等成对功能使用独立的 `prior` 和 `current` 会话、独立图像哈希和独立工具缓存；prior 观察导入当前聚合图时使用与图像内容绑定的命名空间，防止不同检查的节点被误复用。

执行器的缓存只允许复用同一注册表实例、同一图像内容、同一工具参数和同一输入 mask 的成功观察。输入图像变化、mask 变化、模型身份变化或产物校验失败时必须重新运行或拒答。

## 8. 适用条件、冲突和拒答

方法框架把“无法可靠回答”作为一种正式结果，而不是异常路径。典型拒答条件包括：

- 必需工具没有注册或返回 `ToolRefusal`；
- 工具输出无法解析、字段缺失、数值非有限或坐标越界；
- mask、框、点和图像不是同一个坐标系；
- 模型视野截断导致测量不完整；
- 当前 mask 的 owner 与当前 Observation 不一致；
- 两个证据通道冲突，但没有冻结的仲裁规则；
- 成对图像的患者、时间顺序、配准或病灶对应未经核实；
- 试图把原始未校准分数写成临床概率；
- 试图把二维投影关系解释成三维解剖结论。

拒答结果需要记录功能编号、触发步骤、工具、原因、缺失条件和已有证据。对于多功能 episode，单项拒答可以与其他成功功能组成 `partial`，但不能被当作成功 Claim。

## 9. 评估分层

项目把评估拆成互相独立的层级：

### 9.1 工具工程正确性

检查接口 schema、参数校验、坐标回映、单位、缓存绑定、确定性计算、模型官方流程差异、异常处理和拒答。合成 mask、手算值和 metamorphic test 适合验证这一层，但不能证明模型预测准确。

### 9.2 A 工具预测准确性

使用与模型训练来源隔离的人工标注或可信参照评估模型输出。分割可报告 Dice、IoU、HD95；点可报告像素误差；框可报告 IoU、AP/FROC 和中心误差；分类可报告 AUROC、AUPRC、macro-F1；连续测量可报告 MAE、偏差、ICC 或 Bland–Altman。患者级划分、训练数据重叠和适用投照必须在协议中冻结。

### 9.3 组合功能正确性

在 Oracle 输入和预测输入两种条件下分别验证：

- 工具组合是否选对、参数是否传对；
- Relation 数值是否正确；
- 证据是否绑定到正确的图像和 Observation；
- 缺失、冲突、截断和不适用时是否拒答；
- 功能输出是否与独立的功能级参照一致。

“A 工具分别准确”不能自动推出“组合功能准确”，因为组合还可能存在坐标错配、口径不一致、错误仲裁或错误拒答。

### 9.4 大模型消费层

在证据卷宗固定后，才把 EvidenceCard 交给消费模型。应检查：

- 是否引用了正确的 Observation/Relation/Claim；
- 数值、单位、方向和时间关系是否保持一致；
- 是否遵守适用条件和拒答规则；
- 删除、交换、冲突注入或伪造引用后，模型是否能识别证据不足；
- 是否把“未评估”或“有限适用”扩写成未经支持的诊断。

消费模型的文字流畅度不能替代证据依从性和引用正确性。

## 11. 功能组合示例

下面的示例把“一个功能如何组织多个工具”具体展开。代码调用形式依据当前 `run_function_episode()` 接口；输出数值仅用于说明字段语义，不是某张真实病例的运行结果。除特别说明外，这些例子不代表模型已在临床数据上达到准确性要求。

### 11.1 P9：从胸片得到带条件的 CTR

**需求。** 用户问“这张正位胸片的心胸比是多少？”P9 的目标是给出可追溯的比例测量，并报告它是否适用；它不负责仅凭比例诊断心影增大。

**规格与工具链。** `P9.json` 声明四个必需步骤：A24 `classify_view`、A25 `assess_image_quality`、A2 `segment_heart`，以及依赖 A2 心影 mask 的 A12 `measure_ctr`。A12 自动接口以 `Heart` mask 测心宽，并用 CXAS 预测的肋骨内缘测胸廓内宽。程序还会检查投照、质量、mask 来源和测量分量是否自洽。

**证据图。** A24、A25、A2 和 A12 分别产生投照、原始质量量、心影 mask 和 CTR Observation。P9 Relation 将它们合并，保留心宽、胸廓内宽、质量条件、投照和 CTR；Claim 只表示“存在带适用条件的 CTR 测量证据”，并引用该 Relation。

**示意调用和输出。**

```python
result = run_function_episode(
    "P9",
    image_ref="/data/study/cxr.png",
    out_dir="/tmp/p9-case-001",
)
```

例如输出字段可以是 `projection="PA"`、`heart_width_px=120`、`thoracic_inner_width_px=300`、`CTR=0.40`、`status="measured"`、`enlargement=None`、`clinical_interpretation="not_assessed"`。这些数值只演示 CTR 为 `心宽 / 胸廓内宽`，不代表项目的临床阈值。

**拒答边界。** 投照为 AP/lateral/unknown、投照解析失败、质量字段缺失或状态 unknown、心影/相关结构触边或视野截断、宽度无效、CTR 与分量不一致时拒答。即使成功测得 CTR，也不能把模型原始分数转成概率或把比例自动翻译为心脏扩大。

### 11.2 G1：把候选区域定位到图像侧

**需求。** 用户问“结节候选在胸片哪一侧？”G1 输出的是 A6 候选框并集与左右肺 mask 的重叠关系。

**规格与工具链。** G1 依次需要 A1 `segment_lungs`、A6 `detect_abnormalities`，再分别调用 A21 `relate_lesion_to_anatomy` 比较候选与 `Right_Lung`、`Left_Lung`。例如：

```python
result = run_function_episode(
    "G1",
    image_ref="/data/study/cxr.png",
    inputs={"finding": "nodule"},
    out_dir="/tmp/g1-case-001",
)
```

**证据图与正常输出。** A1 两张肺 mask 和 A6 的结节框/mask 是 Observations；两条 A21 Relation 分别记录框并集与左右肺的重叠；G1 Relation 据此形成 `image_sides`，Claim 仅声明候选框的图像侧定位证据。若候选只与图像左侧对应的 `Right_Lung` 重叠，可输出 `image_sides=["image_left"]`，并保留双侧 overlap 数值。

默认不传方向核验信息，所以 `patient_sides` 为 `null`。只有调用方另外提供 `orientation_verified=True`、`patient_right_is_image_left` 和可审计的 `orientation_source`，才会生成方向 Observation 并映射患者侧。

**拒答边界。** A6 未检出或无法解析、候选 mask 与框并集不一致、肺 mask 缺失/空/坐标不一致、候选不与任何肺重叠，都会拒答。A6 的框只是区域候选近似，不是病灶分割；G1 也不表示疾病存在/不存在，更不会在方向未核实时猜患者左右。

### 11.3 P6：保留气胸通道冲突

**需求。** 用户问“有哪些气胸相关影像证据，两个检测通道是否一致？”P6 的核心不是把模型分数平均成一个答案，而是把两个来源各自保留下来。

**规格与工具链。** 必需步骤是 A1 `segment_lungs`、A8 `segment_pneumothorax`、A6 `detect_abnormalities`（finding 固定为 `pneumothorax`），以及依赖肺 mask 的 A19 `measure_lung_symmetry`。

```python
result = run_function_episode(
    "P6",
    image_ref="/data/study/cxr.png",
    out_dir="/tmp/p6-case-001",
)
```

**证据图与正常输出。** A8 提供二值 mask、面积/bbox、阈值、最大像素分数和病例原始分数；A6 提供语义候选框或 parsed negative；A19 提供肺形态镜像相似度。Relation 比较 A8 是否有阈值以上区域与 A6 是否检测到候选，输出四种状态之一：`concordant_positive`、`concordant_no_region`、`discordant_a8_positive`、`discordant_a6_positive`。例如 A8 有区域而 A6 返回 `not_detected` 时，输出 `discordant_a8_positive`，同时仍保留 A8 mask 和原始分数。

**拒答边界。** 任一必需工具拒答、A6 为 unparsed、A8 状态与 mask 面积/bbox/owner/阈值矛盾、A19 没有绑定左右肺观察时拒答。A19 只描述肺 mask 的镜像相似性，不是气胸证据。`concordant_no_region` 也不等于排除气胸；A8 的原始分数未校准，不构成疾病概率。

### 11.4 T1：测量 ETT 尖端到隆突的像素距离

**需求。** 用户问“气管插管尖端与隆突相距多少像素？”这个问题要求使用点坐标，而不是把整条导管区域当成尖端。

**规格与工具链。** T1 当前只调用 A26 `localize_devices`。执行器取 A26 中 ETT 观察的 distal tip、carina 观察的 point，以及 ETT 位置分类观察中的原始分数；直接对两个点计算欧氏距离和有符号垂直差。

**证据图与正常输出。** 这三项是 Observation，T1 Relation 记录输入节点 ID、两点坐标、`tip_carina_distance_px`、向量和原始位置类别分数，Claim 表达“存在一个像素距离测量”。若 ETT 点为 `(x=20,y=40)`、隆突为 `(x=20,y=50)`，欧氏距离是 `10 px`，`carina_minus_tip_vertical_px=10`。例子仅说明坐标计算。

**拒答边界。** ETT presence 分数未达到 A26 screening threshold、状态与阈值不一致、尖端/隆突无效或出界、ETT 线 mask 未绑定当前 ETT Observation、原始分数缺失/非法时拒答。没有可信像素间距就不换算厘米，也没有冻结临床阈值就不说“过深”“过浅”或“位置正常”。

### 11.5 S1：比较两次检查的候选范围和灰度

**需求。** 用户要求比较同一患者两次胸片中的某一候选区域。S1 目前只做满足严格前提后的原始量差值，不自动判断吸收或进展。

**规格与工具链。** S1 在 prior、current 两张图各自独立的 `EvidenceSession` 中运行 A6 候选、A9 框范围、A15 显示灰度统计。工具缓存和 mask 不跨图复用。调用方必须先提供 SHA-256 患者标识、不同 study ID、严格时间顺序、可比投照、已应用的配准、已核实的一对一 lesion match 和共同像素坐标系。执行器校验元数据、图像哈希、图像尺寸和候选绑定；它不自行估计配准或验证病灶匹配的医学正确性。

**证据图与正常输出。** 两个 session 各自产生 prior/current 的候选、范围和灰度 Observations；合并图中 prior 节点使用单独命名空间。另有一个 `paired_study_binding` Observation 保存配对元数据及两图哈希。S1 Relation 计算 prior/current bbox 宽高差、显示灰度均值差，并引用六个图像观察与配对 Observation；Claim 表示“已满足调用方声明的配对前提并获得原始比较量”。例如宽度从 12 px 到 15 px，输出差为 `+3 px`；灰度均值从 80 到 70，输出差为 `-10`。`change_direction` 固定为 `not_assessed`。

调用形式示意：

```python
result = run_function_episode(
    "S1",
    image_ref="/data/study/current.png",
    prior_image_ref="/data/study/prior.png",
    inputs={"finding": "nodule", "pair_metadata": verified_pair_record},
    out_dir="/tmp/s1-case-001",
)
```

`verified_pair_record` 必须满足源码和 S1 规格定义的精确字段契约，不能用上述摘要文字代替真实记录。

**拒答边界。** 患者摘要格式错误、身份或时间未核实、study ID 相同、投照不可比、配准未应用/公共坐标系未确认、病灶匹配未确认、两图尺寸不同、候选未检出/无法解析/有多个框、A6 框与 mask 不一致或任一必需工具拒答时，S1 不创建 Claim。即使运行成功，框是模型候选框而非病灶真轮廓，灰度也未跨设备归一化；不能据此宣称病灶吸收、进展或稳定。

### 11.6 这些示例共同展示的组合规则

五个例子采用同一结构：先由功能规格决定工具和适用前提；工具各自产生带图像绑定的 Observation；功能程序只执行预先定义的测量或比较，并把所有输入 Observation 写入 Relation 的溯源；Claim 的措辞与证据范围保持一致。若证据缺失、矛盾或不适用，则产生结构化拒答，而不是用语言模型补齐视觉事实。

当前已注册的功能为全部 26 项；T4 是 reference adapter，缺少 reference 时拒答。示例没有覆盖的程序也必须以真实输入契约、拒答和证据图测试为准，不能仅凭注册成功推断医学准确性。
